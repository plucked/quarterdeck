| `github_link` | `GitHubLink`: GitHub's mark as a 24 px icon button opening a URL (muted, the text color on hover via a group: an `svg` takes only its own text color), beside the detail's title |
| `bundled_fonts` | `load_bundled_fonts`: registers the static TTFs in `assets/fonts` (OFL; Schibsted Grotesk 400/500/600/700/italic, JetBrains Mono 400/700 + italics) at launch; static cuts because gpui would show only a variable font's default weight |
| `review_queue` | main view: the top bar (sidebar toggle, refresh, title, Restart to update when an update is ready, side panel toggle), the sidebar with Mine / Review / Others tabs atop its lists (`QueueLists`: authored, review requested, reviewed (open PRs the viewer reviewed), others; the Review tab shows `review_tab()`, requested + reviewed once each, newest first, kept in `ReviewQueue::review_tab`; "asks for your review" (badges, Hide review requests) reads only the requested list; `fetched` holds everything found, which the refresh syncs from, and `lists` what the tabs show, `without_hidden_branches` (`hidden_branches.rs`: `branch_pattern_matches`, `is_hidden_by_branch`), redone when the lists or the rules change; Others: `OthersTab` keeps the watched repositories, each one's `OthersFilter`, the passing PRs the rows index into (`shown_list`), the open filter and expanded chip rows; `others_filtering` decides what passes and the chip counts, labels match any picked one, picked or hidden values keep a chip even when no pull request has them; the open filter's chips (`OpenFilterChips`, `ChipMarks`) are counted when the list or a filter changes, never while drawing; `QueueRow::build_others` lists every watched repository, then `OthersFilter` / `NothingShown` rows), pull requests grouped by repository and stack in the sidebar (`QueueRow`, `CollapsedGroups`), selection by id (`SelectionOrigin`), opening stack layers in no list, refresh schedule, restore; owns the detail view |
| `brief_view` | a written brief drawn by free functions, shared by the Brief pane and the gallery: `render_brief_column` (as wide as the pane less 24 px each side: the reader decides the width), status card, lead, widgets (`render_tour`: numbered steps, weight in words, mechanical ones quieter; a diagram wider than the column even at its narrowest scrolls sideways; text measured by `TextMetrics` estimates) and drawn with absolutely placed divs over a `canvas` that paints `DiagramStroke`s (`PathBuilder` curves/polylines, dashes, filled/open heads); - Key bindings: `cmd-,` settings, `cmd-w` close window (settings window handles it), `cmd-r` refresh, `cmd-c` copy (handled by the focused view, e.g. a `MarkdownView` with a selection), `cmd-q` quit, `cmd-b` side panel, `ctrl-cmd-s` sidebar. `cmd-1`/`cmd-2`/`cmd-3` Mine / Review / Others tab. Single keys only in `ReviewQueue && !TextArea` (the queue's context, not while a text area has focus): `]`/`[` next/previous shown file, `v` mark the top file viewed and jump to the next unviewed one, `}`/`{` next/previous stack layer, `c` layer ↔ combined review. The queue handles them and delegates to the detail.
- Settings: a new preference goes in `AppSettings` (field + setter that saves), gets a `SettingRow` on its category's page (new categories: a `SettingsCategory` variant + page), and views read it with `AppSettings::…(cx)` and `observe_global::<AppSettings>`. The main view shows no option controls.
- Markdown: parse once when the source changes (`ReviewQueue::set_selected_index` parses the description), keep `Arc<MarkdownDocument>`, render with `MarkdownView::new(id, document.clone())`. Links open only if `http(s)://`; the text comes from other people.
- Markdown selection: state via `window.use_keyed_state` keyed by (view id, `Arc` pointer of the document), so a new document starts unselected; keep the `Arc` stable while the source is unchanged (`ParsedDescription`). Each frame's text layouts reach hit testing only when the frame paints them (render keeps them as `rendered`, the paint-time `drag_listener` commits them): a virtualized list (the Brief pane, comment cards) renders rows to measure them without painting, and gpui panics on the bounds of a layout never prepainted, which aborted 0.4.0 on a click; drags are tracked by window-wide mouse listeners registered in a `canvas` paint. Copy joins texts with `\n`. A press released without a drag is a link click.
- Review pane layout: the sticky header (title, GitHub mark, activity pill, Diff / Brief) and the diff form one column; the side panel (Files / Review / Actions) sits beside that column at full height, from the top bar down. The side panel shows whenever a pull request is (and the panel is toggled on), its tabs too, so it stays put while another pull request loads; the Files tab says `Loading files…` until the files arrive (`render_files_pending`).
- Review pane: the sticky header shows title + meta; viewed progress shows only in the side panel (the tree header's `x of y viewed` and progress bar), not in the header or the summary bar; the description is collapsed by default and again for each new PR, scrolling inside the header past 320 px. Files are ordered by `FileTree::file_order()` (folders first) once at load, so the tree and the diff share one order and file indexes. The tree (`uniform_list`, 24 px rows) has a progress bar, the filter (`filter_rendering.rs`): a Hide viewed switch, a Kind row (Code/Tests/Generated/Moved, one kind per file) and a Type row (extension, or the name of a file without one; alphabetical by name without the dot, ignoring case; collapsed it shows the 8 with the most files + more), where a click picks a chip (show only the picked ones of that row; rows narrow together), ⌥-click hides it (struck through), counts say what a chip would show given the other row (0 is dimmed), and a summary line `Showing x of y · … · Reset` (or the chip hint) right above the tree, with a ghost `Collapse all` / `Expand all` button at its right (one button that turns into the other, so it fits the narrowest panel; `Collapse all` while any folder is expanded, nested folders included; hidden for a flat list); a file row shows its type icon (`FileFacets::icon`) where a folder row has its chevron; right-aligned columns on every row: added / removed lines (monospace, sized for the largest top-level folder's sums so they line up; a folder sums the files under it; zero is blank), the file's status badge (`render_file_status_badge`, shared with the file header; none for a plain modification), and the viewed box: tri-state for folders (mark all / unmark all); it highlights the file at the top of the diff; clicking a file scrolls to it, switching from the brief to the diff first. The tree button in a file's diff header (`show_file_in_tree`) goes the other way: it opens the side panel on Files (saved, as cmd-b), expands the folders above the file, scrolls the diff to its header so the tree highlights it, and centers its row in the tree. A file the filter hides keeps an empty row range (`DetailRowList::file_start` is `None`), so it vanishes from the diff too; `AllFilesHidden` says why the diff is empty. Tree visibility, Hide viewed and hidden kinds persist (`ReviewLayoutState`); picked chips, file types and collapsed folders reset per PR. The empty diff names what narrows it.
- Avatars: every GitHub username shown is preceded by the person's round `Avatar`: sidebar rows (`#n ·` avatar `author · age`, 14 px), the detail header's meta line (16 px), comment cards (18 px, from GraphQL `avatarUrl`), the Others author chips (14 px).
- Sidebar look: repository headers carry a `RepoMonogram` (first letter on a color picked from the name via `theme::label_colors`), the name, owner, a count pill and a `FoldChevron`; groups after the first start below a divider. A pull request row has an open (green) / draft (grey) ring, its title on up to two lines, `#n · author · age` (`relative_age`) the viewer's `ReviewVerdictBadge`, a Draft pill, then `base ← head` in the code font (each name truncating on its own; none until the branches are known; stack layer rows leave it out); stack headers a drawn stack glyph.
- Sidebar grouping: each tab's list is grouped by repository (`QueueRow::RepoHeader`: name, owner, count; repositories in the order of their most recently updated pull request); clicking a header folds the group (`CollapsedGroups`, with folded stacks), saved as UI state (`FoldedGroups`, restored at launch). Rows under it leave the repository out of their metadata.
- Stacks: the queue's refresh fills `PullRequest::stack` (GraphQL; on failure the last known memberships stay). The sidebar groups a stack under a header at the place of its most recently updated listed layer, with every layer bottom first once its layers are known, one line each (position, title, `#number`) so long stacks stay compact (the sidebar is a variable-height `list`; `rebuild_rows` resets it and puts the scroll position back) (`QueueRow::OtherLayer` for layers the tab's list lacks: muted, clicking opens them; ⇧-click on a layer of the shown stack starts the combined range there, `PullRequestDetail::start_combined_at`); layers asking for the viewer's review carry a Review badge, and the header says how many are yours / to review. The queue keeps the listed stacks' layers (`stacks`): read from the cache at launch, checked with GitHub after each refresh (`fetch_stack.rs`, shared with the detail; free on 304); clicking the header opens the combined review (highest listed layer, from the lowest unmerged one) and highlights it while shown (`DetailEvent::TargetChanged` redraws the sidebar); its chevron collapses the group. The detail reads the stack from the cache, then checks it with GitHub on every shown version (free on 304), and shows the stack bar (layer N of M, ‹ › neighbours, Layer/Combined, the combined range); the sidebar is the stack's map. Opening a layer emits `DetailEvent::OpenLayer`; the queue selects it from a list or fetches it (`pull_request_by_number`, cached, `SelectionOrigin::StackLayer`, survives refreshes). `ReviewTarget::decide`: combined = base of the first layer (the chosen start, else the lowest unmerged) to the head of the shown layer; it waits (`AwaitingStack`) for the layers. Combined viewed marks are their own `ReviewScope`. The review mode persists in the review layout.
- Review comments: a `+` left of each diff line (on hover), or a double click on the line (the side clicked, in a split row; it replaces double-click word selection there), opens the composer under it (shift-click another line's `+` to span lines); the lines of the comment being written or edited are tinted (`comment_range`); cards (`DetailRow::CommentCard`, built by `ReviewComments::cards` and placed by `CommentPlacement`) show GitHub conversations (comments with edit/delete when permitted, draft replies, reply, resolve/reopen) and the user's notes (edit/delete), under their line or, outdated, under the file header. GitHub and local cards show together on a single pull request. New comments go to the destination picked in the composer (or the Review tab), remembered in the review layout (`comment_destination`): GitHub (drafts in `review_notes`, submitted with a verdict and summary as one review; drafts are dropped as GitHub takes them) or Local (notes to copy as Markdown for an agent: file, lines, a diff excerpt with 2 lines of context, the note). Combined reviews are local only. GitHub's conversations are read once per shown PR (one GraphQL request, not cached); edits, deletions and resolving go to GitHub at once and re-read the conversations. Only one editor is open at a time (`CommentEditor`); its row is re-measured as it grows (searched in its file's rows only). Opening, saving, cancelling and deleting a comment rebuild only the affected file's rows (`refresh_comment_files`), never the whole list: a full rebuild re-measures every row and is slow on big PRs.
- Brief: `DetailMode` (Diff / Brief, the header's `SegmentedControl`) swaps the diff column for the brief: the page tabs pinned above (several pages only) and its own virtualized `list` of `BriefRow`s (status, or the shown page's `BriefPageRow`s). How well the reader knows the area (`ReaderFamiliarity`) is picked on the status card and in the footer (`render_familiarity_picker`, a `SegmentedControl` with what the choice does), remembered per repository for the session (`BriefPane::familiarity_for`), sent with the request and named in the footer; picking it re-measures those rows. Briefs persist: `BriefJob` (the background run) stores each written brief with `write_brief` under the target's `ReviewScope`; the file load reads the stored brief (prepared off the main thread) and the shown head (`shown_head_sha`: the combined range's, else `file_set_commits`) with the files, and `show_stored_brief` shows it when the session has none for that target. Above a written brief, `render_brief_version` says the commit it was written for and how long ago, quietly when it is the shown head, marked with Write again when the pull request (or range) moved on, and that the version is unknown otherwise; its right end holds the Report button (pressed while the report panel is open). The queue reads a `BriefIndex` at launch and after `DetailEvent::BriefStored` and marks pull request and stack layer rows with a ✦ (`render_brief_mark`, `LayerMarks`). Report (`render_report_panel` in the pinned bar under the version line, so no list row changes size; `ReportState`: closed / writing in a `TextArea` / saving / saved with Copy path / failed keeping the words) writes the brief's `BriefRecord` with the reader's words via `write_brief_report` on the background executor; the panel closes when another brief or page shows. The steps are `brief_view`'s `ReportHost` trait (open, save, close, copy path) over a `BriefReport` (state + save task), so the detail and the gallery report alike; `view_action` builds the handlers that call a view. The shown page is kept per brief entry (`page_of` / `set_page`, back to the first when a brief is written); `show_brief_page` changes the rows, which resets the list to its top. `BriefPane` keeps one `BriefState` (writing with `AgentProgress`, written `PreparedBrief`, failed) per pull request id + `ReviewTarget` for the session, each with its own run (briefs of different pull requests or targets write side by side): its `Task` plus a `RunCancel` guard that sets the flag `prepare_workspace` and `run_claude` look at every 200 ms (then `SIGTERM`, 2 s grace, `SIGKILL`), so replacing, cancelling or dropping the run kills the `claude` process; a run started over a written brief keeps it (`BriefEntry::replaced`) and Cancel shows it again. The rows remember which brief and page they show (`ShownBrief`), so another brief always starts at its top with the report panel closed. `write_brief` builds the `StudioRequest` from the loaded files (for a combined range, the stack's layers in `first_index..=last_index` as `RequestLayer`s, from the loaded stack, no request) and, on the background executor: for a combined range the layers' descriptions (`read_layer_descriptions`: the cache by repository + number, else one request per layer, cached), `BriefCode::prepare` (the detail's `shown_head_sha`, `prepare_workspace` with the client's token and `change_diff_of` the loaded files, built on the background executor (every file's patch with `---`/`+++` headers); `BriefCode` is the workspace or the reason there is none; any failure gives `CodeAccess::DiffOnly(reason)`, shown in the footer), prompt → `run_claude` in the workspace → `parse_studio` → `PreparedBrief::prepare`; the workspace is dropped (deleted) when the run ends, including on cancel; progress (checkout %, unpacking, reads, writing) through a `futures` channel. Rows are laid out again in `rebuild_rows` and on state changes, reset when they or the brief and page they show differ. Diagrams are fitted to the measured column (`render_column_width_probe`) for the shown brief only: on a width change and when a brief shows; `fit_diagrams` returns the widgets whose size changed, and only their rows are measured again. A file load skips reading the stored brief when the session already has one there. Drawing is `brief_view`'s (`brief_pane_rendering` only lays out the rows; the loaded files are its `BriefDiffs`, `file_lookup`); code shown in the brief is cut from the loaded diff by anchor; an anchor link switches to Diff, expands the file and scrolls to the line's row.
- Pull request actions: the side panel's Actions tab (`SidePanelTab::Actions`, `render_actions_tab`; without a GitHub connection it says so) holds `Merge…` / `Close…`, which open a panel under them (`ActionPanel`; laid out for the panel's width: merge methods one per line, confirmations with the question above the buttons, button rows wrap) that reads GitHub's options when it opens (one GraphQL request): readiness, the repository's allowed methods, merge queue, permissions. Merge offers the allowed methods, `Merge as admin` (bypass rules) when the viewer may and requirements are unmet, and a stacked PR's note that the unmerged layers below merge too; every action is confirmed in a second step. The merge is followed (poll every 1.5 s, up to 3 min); the head branch is deleted afterwards when ticked (ticked by default for a close; for a merge only when the repository does not delete merged branches itself; never for forks or when an open layer above is based on it). A PR already merged or closed offers `Delete branch` while its branch exists. A PR merged or closed here stays selected (`SelectionOrigin::Finished`) so the outcome stays in view. Success emits `DetailEvent::PullRequestChanged` and the queue refreshes.
- Loading indicator: the background load reports `LoadProgress` through a `futures` mpsc channel (checking commits, files n of total from `RevisionCheck`, MB of a combined diff in 256 KB steps, building diffs); the header pill (pulsing dot), a progress line under the header (determinate when the share is known, else sweeping) and a loading card in place of the files show it; stack checks and syntax batches show in the pill too. The sidebar pulses while refreshing or opening a layer.
- Diffs: built on the background executor when files load and when whitespace/highlight settings change (layout/wrapping only redraw); `LoadedFile` holds `Arc`s of file + diff. `FileReviewState` owns viewed/collapsed per file; viewed marks persist with a `PatchFingerprint` and reset when the patch changes. Files over 400 changed lines and viewed files start collapsed.
- Context lines: a hunk header with hidden lines above it is a gap bar (`render_gap_bar`: `↓ 20 lines` below the hunk above, `↑ 20 lines` above the hunk below, `Show all N`; a gap of ≤ 20 shows whole in one click; the top of the file only grows up, the end only down), and `DetailRow::EndGap` is the bar below the last hunk (length unknown until the text is fetched). Added, deleted and binary files have no gaps. The first click fetches the file's text (`fetch_file_text`: cache by blob SHA, else GitHub; head commit from `file_set_commits` or the combined range); `ContextLoads` holds the load state, the lines clicked open while loading (all revealed when the text arrives) and the tasks per file index (reset per load); a cached text found by an abbreviated SHA is used only when the patch matches it (`FileDiff::is_patch_of`), else fetched; a failed cache write is reported on stderr, not fatal. `LoadedFile` keeps the patch's diff, the `FileContext` (text + `RevealedLines`) and its gaps; `diff` is the patch's with the revealed lines (`FileDiff::with_context`), kept across settings rebuilds (`keeping_context_of` carries lines revealed while a rebuild ran). A reveal rebuilds that file's rows only and colors its grown diff in the background. Revealed lines (`LineOrigin::FileText`) get no `+` comment button: GitHub takes comments only on patch lines.
- Syntax colors: after load and after a rebuild, `highlight_syntax` runs one background batch per core and applies each batch as it finishes (matched by the diff's `Arc`, so a rebuilt diff ignores stale colors). Files draw plain until then. A real 99-file / 4.5k-line PR takes ~0.7 s single-threaded; `code_highlights` merges syntax colors with changed-range backgrounds into non-overlapping runs.
- GitHub usage (`fetch_changed_files`, `fetch_combined_files`, `fetch_stack`): files cached for the PR's `updated_at` → no request; otherwise one commit check (`pull_request_revision`, conditional on the stored ETag, free when unchanged) → same commits: confirm the cached files; new commits or nothing cached: fetch all pages and cache. Past `MAX_LISTED_FILES` (3000, GitHub's list limit) the files come from one compare `.diff` download of the PR's base and head commits instead (the PR's own `.diff` stops at 300 files): seed#23891, 17,485 files, 156 MB in ~10 s. Large file counts stay quick: each `LoadedFile` keeps its `FileFacets` (kind, type), viewed marks match through a map, the file at a row is a binary search, and viewed counts read `FileReviewState::viewed_count`. Measured on a real 130-file PR: relaunch 0 core requests, after a comment 1, cold 3. A combined range is read from the cache by its two commits, else one `.diff` download. The queue refresh is 2 search requests + 1 GraphQL request, shown at once, then others' changes per watched repository (issues API, usually 1 request each, since where the repository's last sync this session ended (`OthersTab::synced_until`); the first fetch of a repository pages through all its open items); after it, `delete_expired(AppSettings::cache_ttl)` runs. One refresh runs at a time (one asked for meanwhile runs after it); once GitHub refuses requests (`is_throttled`) the remaining repositories are not asked, and a used-up budget (until it refills) or a `retry-after` holds the timed and activation refreshes back (`RefreshSchedule::hold_until`).
- Flow: show cached queue at launch → refresh from GitHub in background → cache → clean up expired data.
- Panel widths: the sidebar (240–720 px, default 380) and the side panel (220–640 px, default 300) resize by dragging the `ResizeHandle` between panels (the handle is the divider line, not a border, so it overlaps no scrollbar); each owner keeps its width and records it (`record_sidebar_width` / `record_side_panel_width`, batched writes).
- Restore: window placement, panel widths, sidebar visibility, folded repositories and stacks, queue tab, selected PR by id (matched against the cached lists, else a cached PR in no list (a stack layer), then the first refreshed lists, else dropped), detail scroll as `DetailScrollPosition` (row + offset; applied when the files load, so no heights are needed).
- Performance: the detail pane lays out only the rows on screen (`list`, overdraw 600 px, no `measure_all`: measuring every row of seed#16354, 1453 files, blocked the window ~10 s and took 5 GB). The scrollbar uses `ListRowTops` from `estimate_row_tops` (exact for fixed-height rows, wrapped lines by character count at the pane width, typical heights for comment cards), re-estimated when the rows or the width change (62k rows: 9 ms in a debug build). The file tree's folder rows read `FolderSummary`s (lines, viewed state) worked out once per `refresh_rows`, never per frame. Layout and text shaping need the `Window`, so they stay on the main thread; diff building and syntax colors run on the background executor. Collapse/viewed toggles and comment changes rebuild one file's rows and `splice` only the part that changed (`ChangedRows`; comment rows always count as changed), then put the top row back: gpui's `splice` moves the scroll to the start of any spliced range holding the top row; settings/load `reset` and re-anchor on the file at the top. Benchmark (100-file PR, split + wrap, 45 px/frame): 273 ms → 8.3 ms per frame. Scroll mode scrolls each file sideways via a per-file offset on horizontal gestures (rows are separate, so no per-file scroll container).
- Scrollbars: wrap the scroll container in a `relative()` div with the container `size_full()` and a `VerticalScrollbar` beside it: `ScrollbarTarget::Handle` for a div or `uniform_list` (`handle.0.borrow().base_handle.clone()`), `ScrollbarTarget::List` for a `list`. The thumb is painted at paint time.
- Diff selection: `DiffSelection` (side + anchor/head as row + byte) lives in `PullRequestDetail`, so it survives scrolling; cleared on any row rebuild/splice. Each painted code cell registers its `TextLayout` in `CodeSegments` from a paint-time `canvas` (only painted texts, so bounds exist; measured-only rows never register); the registry is cleared in `render`. Drag past the pane edge autoscrolls; split selections stay in one column; copy (`selected_diff_text`) is code only. A press outside code clears the diff selection without taking focus, so the description keeps its own selection.
- Wrapping text in a flex row needs `min_w_0()` on its flex item (see the skill's gpui rules); the detail pane and Markdown list items have it.
- Window display: gpui reports and takes window bounds relative to the window's display, so the placement saves the display's UUID (`display.uuid()`, stable across reconnects) and `launch_app` reopens with `display_id`; a missing display falls back to the main one, and placements that do not fit their display open centered.
- gpui on macOS opens windows by content size but reports `window_bounds` as the frame: save `viewport_size` for windowed mode. With the transparent title bar the content fills the frame, so both match (measured: a 1200×800 window reopens at 1200×800).
- Title bar: the main window's is transparent (`appears_transparent`, traffic lights at 14,13); the queue's 40 px top bar takes its place, leaving 84 px for the traffic lights. macOS keeps dragging the window by the bar's empty parts; a double click calls `titlebar_double_click`. The settings window keeps the system title bar.
- Look: the active theme (see `theme`): green and red never mean added/removed, only success/danger; the diff's `+`/`-` marks take the added/removed colors and line numbers the palette's line-number color; one accent (light blue) for selection and primary actions; secondary actions are ghost buttons; pills (`rounded_full`) for badges, chips and status; cards are `surface` with a strong border; small uppercase `subtle` labels head panel sections; checkboxes are drawn (`Checkbox`), never glyphs.
- UI changes are verified by running the app; view logic that can be tested without a window lives in plain types (`SelectionAfterRefresh`, `SelectionRestore`, `RefreshSchedule`).
